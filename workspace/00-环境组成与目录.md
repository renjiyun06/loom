# 环境组成与目录

## 组成

织境在 Glamorous Toolkit 内承载业务和 Codex 客户端，通过本机 Codex App Server 调用模型。当前使用官方 Glamorous Toolkit v1.1.699 Windows x86_64 便携版。附带的 Node 用于短时命令和检查工具。文件来源、哈希和版本依据见 `../config/runtime-manifest.json`，运行配置见 `../config/runtime.json`。

| 部分 | 当前职责 |
| --- | --- |
| Glamorous Toolkit | 保存业务对象和原生界面，直接发送模型请求，处理工具回调、会话绑定和调用回执。 |
| Codex App Server | 维护模型会话，运行模型轮次，通过 stdio 把工具回调交给 GT。 |
| GT 应用层 | 装载原生界面和业务程序，管理原生对话、邮件、微信、附件、录音与转录。业务故障在各自的状态中报告。 |
| Windows 监管程序 `LoomSupervisor.exe` | 校验当前恢复镜像，直接启动并监测 GT，把其子进程纳入同一 Job，封存已保存的检查点。 |

三个核心进程按 `LoomSupervisor.exe → GlamorousToolkit-cli.exe → codex.exe app-server` 的顺序启动。GT 应用层和 Codex 客户端同在 GT 进程。Codex 按工具执行需要启动 `codex-code-mode-host.exe`，Windows 为相应程序创建 `conhost.exe` 控制台宿主。实际进程总数随工具执行变化。

这套环境可独立启动，不依赖 Mira 后台。Mira 中的工程登记是管理记录，不是本环境的模型调用或执行机制。

## 入口与工作位置

`D:\Loom\workspace` 是 Loom 启动或恢复底层 Codex 会话时传入的统一 `cwd`。主会话和其他命名会话由此加载同一份 AGENTS.md 和按需文档。实际业务工作按以下步骤定位。

1. 根据本次请求确定目标，是活对象、已有程序、文件还是其他工程。
2. 读取相应对象或确认文件位置，核对已有改动和当前状态。
3. 在实际目标所在位置工作。新任务需要磁盘目录时先明确位置，不把产物留在入口目录。

维护织境自身的运行实现时使用本环境的 `src`；处理其他业务时不要因此把 `src` 当成通用业务目录。

| 根目录下的位置 | 职责 |
| --- | --- |
| `workspace` | 环境说明入口和编号文档。 |
| `src/runtime` | 运行时装载、客户端、GT 应用、检查点与原生生命周期适配的初始源码。 |
| `src/tools` | 本机命令入口和检查点校验工具。运行命令通过 GT 的本地接口工作。 |
| `src/supervisor` | Windows Job 监管程序源码及构建入口。 |
| `src/documentation` | 文档目录同步和校验工具。 |
| `src/audio`、`runtime/audio`、`runtime/media` | 本地录音与播放、讯飞转录源码及随环境携带的执行程序。 |
| `src/runtime/conversation-db.st` | 对话 SQLite 存储、旧记录导入和附件接口。 |
| `runtime` | 本环境携带的 Glamorous Toolkit、Codex、Node、监管程序及依赖。 |
| `config` | 运行路径、模式、运行文件来源等配置。 |
| `state/runtime` | 初始镜像、活动副本、执行检查点及恢复指针。 |
| `state/sessions` | Loom 会话、线程绑定、切换记录、调用回执和活动历史。 |
| `state/conversation` | 当前对话程序的持久输入与回答。 |
| `state/mail` | 邮件任务、收发线程、收到的附件和回信附件。 |
| `state/weixin` | 微信绑定、消息、收发附件、语音转写与纠正稿。 |
| `state/audio` | 原音、派生音频、转录订单和结果。 |
| `ipc`、`logs` | 临时通信与实际执行记录。 |
| `backups`、`tests/results` | 备份与验证依据。 |

Codex App Server 沿用 Codex 自己的用户数据目录。在 Windows 的默认配置下，该目录为 `%USERPROFILE%\.codex`，由 Codex 保存登录、配置、技能、插件和原生线程。Loom 的会话绑定仍在 `state/sessions`。

运行中的 `ExperimentRoot` 和 `LoomIPC` 全局对象给出 Glamorous Toolkit 侧实际根目录及通信位置。当前活动镜像位置可查 `Smalltalk imageFile fullName`；启动活动副本与后续另存快照的路径可能不同，不要据目录名猜测当前加载的 image。

## 版本管理

Git 仓库位于 Loom 根目录，记录源码、启动脚本、测试源码、文档和源码依赖的静态资源。Loom 的说明和专题文档在 `workspace` 下维护。所有 Git 跟踪内容均由运行时身份为 `main` 的 Loom 会话维护。主会话在活镜像中修改系统代码后，需要同步到对应的磁盘源码，Git 才能记录改动。

镜像、会话、运行程序、下载包、本机配置与凭据、日志及测试产物仍放在各自的本机目录。Git 历史用于追踪源码和文档，运行现场由 [保存恢复与生命周期](03-保存恢复与生命周期.md) 所述的机制保存。

### 提交时机与范围

主会话每完成一项改动，应先核对差异，再按影响范围验证，验证通过后提交。文档改动检查目录与链接，代码改动验证实际受影响的行为。一个提交对应一项可独立说明的改动，只暂存与该项改动相关的文件。提交后通过 `git status` 和 `git log -1` 核对结果。

### 提交消息

标题统一采用 `类型(范围): 简短说明`。类型和范围用小写英文，说明用一句中文交代具体改动。范围指主要改动区域，例如 `workspace`、`codex`、`runtime`。需要说明原因、迁移或验证时，在标题后空一行，再写正文。

| 类型 | 用途 |
| --- | --- |
| `feat` | 新能力或行为 |
| `fix` | 修复问题 |
| `refactor` | 调整代码结构 |
| `docs` | 修改文档 |
| `test` | 修改测试或验证脚本 |
| `chore` | 构建、依赖或仓库维护 |

示例为 `docs(workspace): 约定 Loom 的 Git 提交流程` 和 `fix(codex): 恢复已保存的会话绑定`。

## 启动与界面

桌面 **织境** 快捷方式经 `open-loom.vbs` 启动隐藏的 PowerShell，运行 `open-loom.ps1`，再由 `start.ps1` 启动 Windows 监管程序或复用已就绪实例。随后 `src/runtime/open-desktop.mjs` 通过 Node 短时运行并唤出 GT 主窗口，启动器在窗口就绪后退出。GT 应用装载流程在主窗口内恢复已打开的标签。关闭过的对话标签可点右上角的聊天图标重开。后台运行时重开主窗口会恢复图形循环，最小化的窗口则恢复显示。

```powershell
& D:\Loom\start.ps1 -Gui
& D:\Loom\start.ps1 -Headless
& D:\Loom\stop.ps1
```

不带模式参数沿用上次模式。切换模式会先保存并停止旧实例，再恢复到新模式。关闭对话标签只关闭呈现，消息处理与当前会话继续保留；退出 Glamorous Toolkit 的原生流程见 [保存恢复与生命周期](03-保存恢复与生命周期.md)。

GT 的 Codex 客户端就绪后，`src/runtime/applications.st` 装载应用并恢复界面。对话和录音队列都是 GT 的业务 Process，原生音频和转码工具按操作启动。可以在 GT 执行 `LoomApplications reload` 从磁盘重新装载应用代码，GT 和 Codex App Server 继续运行。

当前官方便携版位于 `runtime/gtoolkit`，下载 ZIP 保留在 `downloads`。官方版本与校验和在 `config/gtoolkit-release.json`；工具包镜像版本通过 `GtImage version asString` 核对，启动器或 VM 自身的组件版本与它不同。GT 的上游依赖文件保留厂商原名，不自行改名。
