# 对话程序与调用机制

## 当前程序

| 对象或类 | 职责 |
| --- | --- |
| `LoomConversation` | 当前正在运行的对话对象。 |
| `LMConversation` | 接收输入、等待、调用模型并保存回答。 |
| `LMConversationUI` | 采用 GT Bloc/Brick 的原生对话标签。 |
| `LMVoice` | 本地录音、导入、播放及转录操作。 |
| `LoomGtMail` | 轮询配置的邮箱，调用 Codex 拟写回信，并保存收发历史。 |
| `LoomGtWeixin` | 接收微信消息，将回复和附件发回绑定的聊天。 |
| `LoomCodex`、`LMCodexClient` | GT 业务程序调用模型的入口，沿用持久线程和调用回执。 |

对话类位于 `Loom-Conversation` 包。客户端、对象调用、会话管理和 GT 内的 App Server 连接都位于 `Loom-Codex` 包。

GT 里的程序决定入口、运行分支和结果去向。聊天是当前程序采用的交互方式，用户输入、最终回复和业务状态由 Loom 管理。同一份 Loom 历史可以先后对应多条底层 Codex 会话。

## 对话循环

1. `submit:` 保存用户输入并唤醒等待的程序。
2. `run` 寻找尚未产生回答的输入，没有输入时等待 Semaphore。
3. 语音输入等到讯飞转录出文字后才就绪。`answer:` 用 `LoomCodex session: #main` 选中会话，并在这条底层 Codex 会话中先纠正转录，保存纠正结果。
4. `preparePrompt:` 从就绪消息准备本次上下文，录音消息保留 `kind: audio` 标记并使用纠正后的文字。`replyTo:usingContext:` 把消息和上下文传给同一条底层会话。`process:` 按返回的浏览器处置值完成本轮，再发布答复并回到循环。

正式回复通过 `loomReturn` 交回一个字典，`text` 是用户看到的 Markdown 正文，`browserAction` 取 `none`、`keep` 或 `close`。本轮未使用浏览器时用 `none`，后续可能接着使用或用户正在操作时用 `keep`，确认用完时用 `close`。仍可接收旧的字符串回复，按 `none` 处理。

收到 `close` 时，Loom 先将待发布的答复保存到 SQLite，再在同一个 Loom 会话和底层 Codex 线程中发送 `closeBrowserUsedFor:`。实参是原答复调用的请求 ID。Codex 沿用该轮的工具，核对并关闭对应的浏览器，然后返回关窗结果。Loom 发布原答复，关窗未确认时在答复旁显示状态。恢复时，若遇到留在 SQLite 中的待发布答复且原执行现场没有继续，发布原答复并标明关闭状态待确认。

等待新消息发生在 Glamorous Toolkit 中，不通过持续调用模型维持循环。关闭对话标签不终止这个程序。

消息和回复保存在 `state/conversation/conversation.sqlite`，按消息 ID 对应并按发送序号读取。首次升级时，存储层可在一个事务中导入旧 `inputs` 和 `replies` 下的 JSON。当前环境已完成迁移并清理旧目录。界面读取 SQLite，对话历史和模型线程上下文各自持久化。

GT 应用层通过 Windows SQLite 初始化对话存储，聊天入口独立报告启动或迁移错误。修复存储或修改业务源码后，可在 GT 中执行 `LoomApplications reload` 热装载。已经进入旧方法的调用可能继续用旧逻辑，直到返回。

点输入栏的回形针可选一个或多个本地文件。也可以在输入框按 Ctrl+V，把资源管理器里复制的文件或剪贴板里的截图和图片加为待发送附件。粘贴的图片以 PNG 保存，普通文本仍插入光标处。待发送的文件在输入框内顶部排列成一行，可逐个移除。长文件名截短时优先保留扩展名，悬停可看全名。点「+N」可展开其余文件。正文可以留空。发送时复制原文件到 `state/conversation/attachments/<附件ID>/`。消息只携带按添加顺序排列的 `attachmentIds`。数据库的附件记录保存显示名及相对于 `state/conversation` 的路径。已发送的附件在正文下方以右对齐的卡片显示。点击卡片打开附件。文件名在窄窗口可以换成两行，过长时在中间省略，悬停可查看完整名称。原文件移走后可以通过已保存的副本打开，副本缺失时卡片会提示。

对象调用沿用 `replyTo:usingContext:`。调用期间从 `loomMessage` 取得 `attachmentIds`，用 `LoomConversation attachment: id` 查附件记录，再通过 `LoomConversation fileForAttachment: attachment` 得到本地文件。发送给 Codex 的模型轮次沿用原调用协议。GT 消息存储在 `src/runtime/conversation-db.st`。

## 模型调用与工具返回

`LMCodexClient` 将请求写入 `ipc/codex-requests`。GT 的请求进程直接通过 stdio JSON-RPC 调用 Codex App Server，把轮次回执写入 `ipc/codex-responses`。`ask:` 返回文本。开始连接等单个协议请求有等待上限。正常运行时，模型轮次等待完成或明确的连接故障。

```smalltalk
LoomCodex lastResponse
```

回执可包含 request ID、thread ID、turn ID、模型、时间和错误。当前程序串行处理模型请求。App Server 通过同一条 JSON-RPC 连接发出 `runtime_eval` 调用，GT 在独立的 Process 中求值并沿该连接回送结果。模型等待工具时仍在同一轮调用中。本机命令另用 `ipc/mailbox` 和 `ipc/results`。

不要在这个回调内递归调用同一个模型客户端。需要独立业务进程的场景和反射示例见 [运行环境的观察与演进](01-运行环境的观察与演进.md)。

### 通过 Smalltalk 消息调用 Codex

在独立的 GT Process 中，程序用 `LoomCodex session:` 选中命名会话，再向它发送一个未定义的 Smalltalk 消息。Loom 在 GT 中保留方法名、任意个数的活对象实参和调用方上下文，本轮初始文本只有「Loom 调用了你。」。Codex 按 AGENTS.md 从运行时工具查阅现场。

```smalltalk
"优先选原始资料，按与问题的相关程度排序。"
selected := (LoomCodex session: #sourceResearch) selectSources: sources for: researchQuestion.
^ selected collect: #url
```

这次调用期间，`runtime_eval` 提供业务调用帧 `loomCaller` 和原始消息 `loomMessage`，由 Codex 通过 Smalltalk 反射查阅调用现场、实参和下游代码。用 `loomReturn value: anObject` 提交一个已有对象或新构造的对象，`nil` 也可以显式提交。工具确认前会保存含结果的检查点。Loom 通常在轮次结束后交回已保存的对象。轮次在结果保存后明确失败时，回执带有 `partialFailure` 和该轮次的 `turnStatus`。结果已保存且轮次连续静默 30 分钟时，Loom 可提前交回对象，回执带有 `releasedAfterSilence` 和 `partialFailure`。绑定和工具参数见 [工具技能与能力发现](04-工具技能与能力发现.md)。

业务方法和对象类型由调用方表达。GT 对话、邮件和微信入口都通过 `LoomCodex session: #main` 调用 Codex。它们共用这个客户端的互斥锁，各入口负责自己的消息队列和回复发布。

轮次明确失败且没有保存返回对象，或成功结束却缺少返回对象时，共享调用层在原 Codex 会话发起 `recover: originalInvocation after: failedAttempt`。每一轮仍以「Loom 调用了你。」启动。恢复调用的两个实参是原调用和最近一轮的回执。Codex 先用 `originalInvocation message` 和 `originalInvocation caller` 读取原始入口、用户消息、实参及返回约定，再用回执里的请求 ID 核对上一轮的活动和工具结果。各轮回执可通过 `originalInvocation attempts` 取得。需要更多前文时，沿原调用的上下文对象查桌面对话、邮件或微信记录。

```smalltalk
originalInvocation activities
 activitySummariesForCall: (failedAttempt at: 'id') before: nil limit: 20
```

查询按该次请求 ID 返回活动摘要。需要翻看更早的活动时，把当前页首条的 `seq` 传给 `before:`。用 `originalInvocation activities activityDetailAt: sequence` 查看指定活动的详情和已保存的工具结果。活动对象的 `databaseFile` 也可用于按原调用历次请求 ID 做自定义只读查询。接手前根据这些记录核对相关写入或投递的实际状态。

恢复轮次遇到同样的结果缺失会继续恢复。每轮有独立请求 ID，恢复请求中的 `originalRequestId` 指向第一次尝试。原业务程序在同一调用点等待，客户端在整个恢复过程中持有同一把会话锁。同一会话的其他调用会等待锁释放。Loom 退出触发的中断、没有结束回执的轮次和连接故障沿各自的处理路径。

### 回复上下文和历史查询

`LoomApplications replyContextFor:from:` 为桌面对话、邮件和微信构造 `LMReplyContext`。用 `source` 和 `messageId` 查看当前消息的来源和标识。邮件任务已知的 `threadId` 对应织境的邮件往来线程。桌面对话的 `prompt` 保存本轮准备好的文字。

各入口通过 `usingContext:` 把这个活对象交给 Codex。需要前文时，Codex 可以沿对象和方法查相关业务记录。各历史对象的 `databaseFile` 返回实际存储文件，可只读打开并按当前需求查询。方法注释说明各库的记录关联和关键字段。邮件或微信尚未装载时，对应对象为 `nil`。

| 上下文方法 | 返回对象及常用查法 |
| --- | --- |
| `conversation` | 桌面对话对象。用 `records` 读消息和回复，用 `speechCorrectionAt:` 按消息 ID 读取录音纠正稿。 |
| `mail` | 邮件对象。用 `threadHistory:` 按线程查往来，用 `searchHistory:` 按主题或正文查候选。 |
| `weixin` | 微信对象。用 `recentHistory` 读取最近 40 条消息及相关附件和回复状态。 |
| `activities` | 运行活动对象。用 `activitySummariesForCall:before:limit:` 按请求 ID 查活动，用 `activityDetailAt:` 读活动详情。恢复轮次也可以从原始调用获取这个对象。 |

## 邮件收发

织境通过 163 邮箱的 IMAP 和 SMTP 收发。后台扫描收件箱的未读邮件，只处理配置中指定发件人的来信，跳过自动生成的邮件，并依据 IMAP 标识及 `Message-ID` 去重。第一次配置时，在本机的 `config/mail.local.json` 填写下列字段。配置和授权码留在本机。

| 字段 | 值 |
| --- | --- |
| `python` | 本机 Python 可执行文件的绝对路径。 |
| `account` | Loom 用于收发的 163 邮箱地址。 |
| `sender` | 允许发来请求并接收回信的邮箱地址。 |
| `pollSeconds` | 两次轮询之间的秒数，省略时用 30 秒。 |

163 邮箱的客户端授权码从当前 Windows 账户的凭据管理器读取，通用凭据目标为 `Loom/Mail/IMAP/<account>`，其中邮箱地址用小写。首次写好配置后，在 GT 执行 `LoomApplications reload` 即可装载邮件入口。运行中的邮件管理器在初始化时读取 Python 路径和轮询间隔，改动这些字段后重启 Loom 生效。用 `LoomGtMail status` 看最近的轮询状态，用 `LoomGtMail transport: 'check'` 检查 IMAP 和 SMTP 登录。

邮件任务通过 `replyToMail:usingContext:` 交给 Codex。它用 `loomReturn` 提交含单行 `subject` 和正文 `text` 的字典，也可以附上 `attachments`。每个附件用 `path` 指定当前任务 `attachmentDirectory` 内的绝对路径，可用 `name` 指定收件人看到的文件名。Loom 校验、复制并发送附件。如果首次校验发现附件有误，会把草稿和错误交给 `correctMailReply:for:usingContext:` 纠正一次。再次校验失败时，保留草稿并记录 `validation_failed`。

`state/mail/mail.sqlite` 的 `mail` 表保存待处理任务、草稿和投递状态，`mail_messages` 表保存收发正文、邮件线程及附件引用。来信附件在 `state/mail/attachments`，本次回信的工作目录在 `state/mail/outgoing`，通过校验的回信附件副本在 `state/mail/outbox`。Loom 用邮件头里的 `In-Reply-To` 和 `References` 关联往来。SMTP 接受后才记录 `sent` 和发件历史。发送过程中断仍处于 `sending` 的记录，留待核对投递结果。

## 微信消息与附件

个人微信可通过 ClawBot 和腾讯 iLink 连接织境。绑定者在 ClawBot 窗口发文字或附件，GT 后台通过 `LoomCodex session: #main` 调用 Codex，再把回复发回原聊天。普通消息使用 `replyToWeixin:usingContext:`。带语音的消息使用 `replyToWeixinVoiceAndReturnCorrectedTranscripts:usingContext:`，由 Codex 在同一轮根据相关上下文纠正微信附带的转写，再交回回复和纠正稿。三个入口共享 Loom 的 `main` 会话。微信入口的对话记录保存在自己的 SQLite 数据库，可按需用 `LoomGtWeixin recentHistory` 查看最近 40 条。

`config/weixin.local.json` 配置本机 Python 的绝对路径，字段名为 `python`。绑定窗口还使用 `qrcode`，可安装到 Loom 的本机运行目录。下面的 `$python` 设为配置中使用的解释器。

```powershell
& $python -m pip install --target D:\Loom\runtime\weixin qrcode==8.2
& $python -B D:\Loom\src\tools\pair-weixin.py
```

在 GT 执行 `LoomApplications reload` 即可装载微信入口。用准备绑定的手机微信扫一扫电脑上的码，再在微信中确认。提示需要验证码时，在电脑上的绑定窗口输入手机显示的数字。看到「微信已绑定」后，发一条消息即可验证入口。凭据用当前 Windows 账户加密，和消息、轮询游标一起保存在 `state/weixin/weixin.sqlite`。授权失效后可再次运行绑定程序恢复。

收到的图片、文件、视频与语音原件保存在 `state/weixin/attachments/inbound`，`attachments` 表按消息 ID 记录文件名、相对路径和状态。微信随语音提供的转写保存在对应附件的 `transcript` 字段，并随消息交给 Codex。这个字段也用来区分原转写和同一条消息里另外输入的文字。模型调用的 `attachments` 可读取已保存附件的本地路径，下载失败的附件仍有状态记录。纯附件消息也可处理。

语音轮次在 `correctedTranscripts` 中返回有转写的语音纠正稿，同时交回正式回复。纠正稿按原语音附件 ID 写入 `state/weixin/weixin.sqlite` 的 `attachments.corrected_transcript` 列，与回复一起入库。查看 `LoomGtWeixin recentHistory` 时，对应附件的 `correctedTranscript` 字段就是纠正稿。微信收到的是正式回复和指定的回复附件。

纯文字回复可返回字符串。带附件的回复返回带 `text` 和 `attachments` 的字典，至少提供文字或一份附件。指定的附件需要放在本次调用给出的 `attachmentDirectory` 中。织境复制到 `state/weixin/attachments/outbound` 后上传，保存每份附件的回执。文字和媒体分条发送。常见图片和视频以对应媒体类型发送，其他内容（含音频文件）按文件发送。当前单份附件上限为 50 MiB。

`LoomGtWeixin sendNotification: text` 可在桌面对话处理期间向已绑定的微信聊天另发一条文字通知。回复调用中也可以从上下文取对象，再发 `context weixin sendNotification: text`。通知使用当前绑定下最近一条带会话令牌的微信来信，正文最多 1900 个字符。尚无可用来信时返回 `missing_context`，用户可先向微信机器人发一条消息。

通知返回带 `id` 和 `phase` 的字典。获得微信消息 ID 时返回 `accepted` 并记录 `serverReplyId`。发送结果未知或缺少微信消息 ID 时，分别记录 `delivery_unknown` 或 `delivery_unconfirmed`。已尝试的通知在 `notifications` 表中保存，可以用 `notificationReceiptAt:` 按通知 ID 回看。需要重试或换会话接手时，可以用 `sendNotification:id:` 传入同一个 ID 和正文，从已保存的记录取得回执。重启将未确认是否完成的发送记为 `delivery_unknown`。

GT 后台状态通过 `LoomGtWeixin status` 查看，队列状态通过 `LoomGtWeixin queueStatus` 查看。消息和下一次轮询要使用的游标在同一个事务保存，并按微信消息标识去重。缺少回复所需会话信息的消息记为 `missing_context`。重启会继续处理待答复消息及已保存但未尝试发送的回复。已经进入模型调用的消息若中断，状态记为 `interrupted`。发送中断或微信应答缺少消息标识时，状态记为 `delivery_unknown` 或 `delivery_unconfirmed`，留待核对。微信返回消息标识后记录 `accepted`。接口行为依照腾讯的公开文档。 [腾讯 iLink 协议说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md)

## 原生界面

GT 主窗口右上角聊天图标打开或选中「织境对话」标签。入口沿用 GT 的 `emphasizedChat`，标签本身以同一个图标表示，操作区保留关闭按钮。GT 原有聊天入口不再展示，避免两个聊天入口并列。桌面快捷方式本身只负责启动或唤出整个环境。

在 GT 主界面顶部菜单打开 Playground，输入并执行：

```smalltalk
LoomConversation open
```

「织境对话」直接从消息与活动区开始。左侧按消息展示 Markdown，正文 14、活动 13、辅助文字 12。复制和 Markdown 源码操作不执行内容。右侧实时显示进度、工具调用及异常，点开条目可查看参数与结果，展开状态会保留。宽屏时，把鼠标移到对话区和活动栏之间会显示分隔线，左右拖动可调整活动栏宽度。输入框按 Enter 发送、Shift+Enter 换行，小键盘 Enter 同样适用。空白消息不发送，长按 Enter 不重复发送。一轮处理期间，发送按钮、回车发送和录音确认暂不可用。可以先编辑草稿，当前一轮结束后再发送。快捷键提示在输入框底部，与输入占位文字左对齐。回复发布前持续显示「正在处理」，发布后展示完整正文。中文使用 Microsoft YaHei UI。发送按钮旁的麦克风可展开录音条。录音发出后，同一条消息显示可播放的原音，并依次显示「正在转录」「正在纠正」和纠正后的文字。纠正完成后自动进入正式处理。详见 [长录音消息与转录](07-长录音消息与转录.md)。

在 Inspector 底部执行 `self state` 或 `self records` 可检查对话状态和记录。也可执行 `D:\Loom\runtime\node\node.exe D:\Loom\src\tools\open-conversation.mjs` 打开标签。重复打开选中同一个标签；关闭后重开保留历史与未发送草稿。草稿随镜像检查点保存，正常保存重启可恢复；它不是已经提交的持久消息，异常退出只能恢复最后成功检查点中的草稿。当前没有网页对话入口。

`LoomConversationWindow` 是沿用的界面控制对象名，不代表另一个操作系统窗口。`presentationSpace` 是供 GT 原生标签承载的虚拟 `BlSpace`，`hostWorld` 指向实际主窗口。切到其他标签时刷新继续；关闭标签后刷新进程结束，重开重新启动。启动只在界面功能版本落后时升级界面，不重建对话模型或切换 Codex 会话。

活动面板顶栏的齿轮打开运行设置。模型与思考强度用下拉菜单选择，Fast 通过开关控制。默认是 GPT-6.2-Sol、High、Fast 开启，保存在 `config/codex.json`。界面使用本机 Codex 模型目录显示可用选项，保存后从下一次调用生效。顶栏的会话切换按钮切换默认对话会话的底层 Codex 会话。Loom 的历史继续按原来的记录追加。

顶栏左侧显示上下文占用和账号周额度的剩余比例，右侧保留会话切换和设置按钮。上下文用当前底层线程的最近一次 token 用量和模型报告的窗口大小估算，快照按线程保存在 `state/sessions/sessions.sqlite`。新线程尚无快照时显示横线。周剩余从 App Server 报告的 7 天额度计算，后台更新，切换线程时继续显示账号额度。

## 流式回复与活动历史

Loom 将 Codex 工具、进度、流式回复项和手动会话切换统一写入 `state/sessions/sessions.sqlite` 的 `loom_activities` 表。每条活动按首次写入的顺序展示，同一调用与条目的后续事件更新原记录。

GT 主窗口右上角的「运行活动」图标打开独立标签。左栏可选「全部会话」或某一条已登记的 Loom 会话，右侧按时间显示活动及其会话标识。活动条目可展开查看工具参数、结果和状态。标签初次加载最近 100 条活动，「加载更早」从同一张表读取历史并保留阅读位置。对话右侧按 `main` 的范围读取活动。

旧版本的活动已随迁移写入 SQLite。现行 GT 活动记录由 App Server 的协议事件产生，历史活动从 SQLite 读取。

GT 按会话、轮次和条目记录 App Server 事件。两个活动视图在后台从 SQLite 分页读取摘要，并按变更版本读取更新的条目。Codex 的最终文字以「最终回复」显示，展开条目可阅读正文，已有的最终回复也可从历史活动中查看。已加载的范围和翻阅位置由各个视图维护。展开条目时，在后台按记录读取并格式化内容。图形队列只应用列表和详情的更新。对话区的正式答复在对话流程发布后从消息记录读取。

对象调用失败时，活动栏以原业务调用的请求 ID 记录一条异常活动。恢复开始后显示「Codex 轮次失败，正在恢复」，连续恢复会更新同一条的次数，成功时改为「Codex 调用已恢复」。轮次失败前已经保存对象时显示「Codex 轮次异常，结果已交回」。最终报错时显示「Codex 调用未完成」。这些状态写在 `loom_activities`，展开可从 `calls` 读取各轮请求 ID、状态和错误，重启后仍可在活动历史中查看。

App Server 一次执行一个由 Loom 提交的 Codex 轮次。轮次获确认后，Loom 按 `turnId` 跟踪最近一次进展。新的条目开始或结束、文字或思考摘要增量、计划更新和保存业务结果都会刷新计时。连续 30 分钟没有进展会追加一条活动，写明最后观察到的阶段。每段静默只写一次，恢复进展后新活动继续按顺序追加，原记录留在 `loom_activities`。

达到静默门槛时，如果业务结果已经持久化，Loom 自动发出中断请求，直接交回已保存的对象，记录为部分异常并保留原来的 Codex 会话绑定。交付无需等待中断回执或轮次结束事件。后续模型请求如遇到旧轮次仍在结束过程中，会等旧轮次的结束事件再提交。

尚未保存结果的对象调用达到静默门槛时，Loom 在后台探测 Google 的 HTTPS 连通性。单次请求最多 5 秒。探测失败时，活动显示正在等待网络恢复，每 15 秒重试。原轮次照常运行，收到进展、保存结果或确认轮次结束时，就结束这次网络等待。

如果探测从失败转为成功，Loom 从恢复时刻再观察原轮次 30 分钟，活动仍保留最后一次实际进展。如果又达到静默门槛，Loom 重新探测。本次静默检查的首次探测成功时，Loom 复查原轮次是否仍在运行、是否仍然静默、结果是否尚未保存。条件仍满足时自动请求中断，等待该轮次的 `turn/completed`。旧轮次确认结束后，Loom 交回期间已保存的结果，或在缺少结果时为同一个 Loom 会话新开 Codex 会话，通过 `recover:after:` 接手原调用。

活动条目使用统一的 Lucide 图标和紧凑的展开区域。工具条目显示名称、状态和耗时。执行失败时，状态文字显示为红色。点击条目可展开参数与结果。阶段预览按栏宽显示省略号，展开读取全文。活动列表为空时显示空态提示。结构化凭据字段在投影中隐藏。

思考条目在没有摘要时也显示状态。收到 Codex 提供的摘要后，同一条目显示「思考摘要」。升级时会将已保存的空正文思考条目设为可见。上下文压缩收到开始事件时写入活动库，显示「正在压缩上下文」。收到同一压缩条目的结束事件时更新原记录，显示「上下文压缩已结束」。

关闭标签停止界面阅读进程，重新打开后从持久活动表恢复展示。镜像恢复沿用原 Codex 线程。活动存储、查询与视图分别由 `src/runtime/codex-activity.st`、`codex-controls.st` 和 `activity-timeline.st` 承载。

## Markdown 与原生条目

LMChatStyle 和 LMMarkdownView 提供聊天专用只读渲染，支持标题、段落、列表、引用、表格、粗体、斜体、链接、行内代码及代码块。未完成的代码围栏可持续显示，代码块只展示和复制，不编译、求值或接入交互式代码编辑能力。鼠标悬停在可点击的链接文字上时显示手形光标，点击链接打开浏览器或本地文件。

LMConversationMessageView 和 LMConversationActivityView 是可复用的列表条目。用户消息通过右侧气泡区分，气泡下只显示发送时间。已完成的回复直接呈现正文，处理中或未完成的回复显示对应状态。消息与活动按稳定 ID 对齐，未改变的条目不重新绑定。工具展开及详情标签在行复用后保留。图形线程只应用投影，不读取整份事件日志。用户离开正文底部后，新消息由输入框上方的「有新内容 · 回到最新」提示。点提示或滚回底部恢复跟随。活动列表在底部自动跟随新事件，向上查看时暂停跟随，滚回底部恢复。

渲染后的同一条回复支持跨段落拖选和复制。点按回复下方的复制按钮会复制整条回复，成功时图标短暂变为对勾。

正文和输入区共用左右边距，使用居中的 1080 宽阅读容器，视口达到 1600 时上限为 1160。短用户消息按字形宽度收缩并显示本地时间。正文原生行盒约 25 高，输入区按内容在 62 至 150 之间增长。代码块和宽表格在块内横向滚动。视口不超过 800 时仅显示对话正文，更宽时活动栏自动并排显示。

### Loom 图标库

新定制页面优先使用 Lucide。`assets/icons/lucide/icons` 收录固定版本的官方 `lucide-static` SVG，导入时将紧凑路径转为 GT 可读的等效写法。版本、来源、包摘要、路径处理脚本和许可证记录在上一级目录。原生页面通过 `LMIcons` 按文件名取得图标，默认大小为 16，颜色为中性灰。读取和渲染都在本地。

```smalltalk
LMIcons iconNamed: 'search'.
LMIcons iconNamed: 'copy' size: 16 color: (Color gray: 0.45).
LMChatStyle iconElementButton: (LMIcons iconNamed: 'code-xml')
 title: '查看 Markdown 源码'
 action: [ "打开当前页面的源码视图" ]
```

SVG 的轮廓由 Bloc 原生绘制，同一图标可以在不同按钮上使用不同大小和颜色。会话回复的复制和源码按钮已采用这套图标。HTML 页面可按相同名称使用对应的 SVG 文件。升级图标包后运行 `tests/native-lucide-icons.st`，核对整套图标都可从原生入口加载。

## Loom 会话管理

GT 主窗口右上角的会话管理图标打开独立的「会话管理」标签。系统会话有持久的唯一标识，可登记命名会话并查看它的运行状态、当前底层 Codex 会话及历次接续。`main` 排在首位，也是当前原生对话程序选择的会话。任何会话都可以通过程序提供的入口与使用者沟通。修改决定 Loom 系统行为的代码由 `main` 承担。旧版 `conversation` 升级时原地改名为 `main`，保留 `default` 客户端绑定、底层 Codex 会话和历史活动。

```smalltalk
result := (LoomCodex session: #failureRecovery) handle: failure.
LoomSessions list.
LoomSessions show: #failureRecovery.
```

`session:` 接受字符串或 Symbol，首次使用登记该标识，后续返回同一个 GT 客户端。有效标识由字母或数字开头，可含字母、数字、点、下划线和连字符，最多 96 个字符。命名会话各有独立的 Codex 绑定，GT 按轮次串行执行。对象调用在业务 Process 中进行。查询通过独立的本机管理通道进行，模型轮次运行时仍可使用。

空闲时可切换它的底层 Codex 会话，下一次调用建立新的底层会话。Loom 标识、历史和其他会话保留。异常恢复与回执规则见 [保存恢复与生命周期](03-保存恢复与生命周期.md)。

如果确认运行中的对象调用已经卡住，可以在「会话管理」中选中该 Loom 会话，点击「新开 Codex 会话继续」。该动作绑定当前请求 ID。Loom 记录接手请求，向旧轮次发出中断并等待它的结束事件。已确认保存的对象可以交回原调用。旧轮次结束时仍缺结果，则在同一个 Loom 会话里新开 Codex 会话，用 `recover:after:` 恢复原调用。后续任务在原会话锁上排队。右侧恢复活动展开后可查看各轮的请求 ID、Codex 会话和轮次结果。

本机也可运行 [manage-sessions.mjs](../src/tools/manage-sessions.mjs) 的 `list`、`show <id>`、`register <id>`、`rotate <id>` 和 `recover <id> <request-id>`。当前运行的请求 ID 可从 `show` 返回的 `call.requestId` 读取。
