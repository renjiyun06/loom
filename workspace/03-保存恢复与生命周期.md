# 保存恢复与生命周期

## 持久状态

| 状态 | 当前保存位置与含义 |
| --- | --- |
| Glamorous Toolkit 执行现场 | 镜像中的对象、方法、进程与调用栈，由已提交检查点恢复。 |
| Loom 会话、Codex 绑定及调用回执 | `state/sessions/sessions.sqlite` 维护持久的 Loom 标识、每条会话的当前 Codex 绑定和历次接续，以及调用结果。Codex 在自身的用户数据目录保存原生线程。 |
| Loom 活动 | `sessions.sqlite` 的 `loom_activities` 表按顺序保存活动与会话切换。切换登记和活动行在同一笔事务里提交，重开后从数据库恢复。 |
| 对话消息 | `state/conversation/conversation.sqlite` 保存输入、回答和附件引用。`state/conversation/attachments` 保存附件副本。备份和恢复聊天记录时两者一起处理。运行时备份数据库须使用 SQLite 备份机制，或在保存退出后复制。 |
| 邮件 | `state/mail/mail.sqlite` 保存邮件任务、草稿、收发线程与附件引用。`state/mail/attachments` 保存来信附件，`state/mail/outbox` 保存校验后的回信附件。 |
| 微信 | `state/weixin/weixin.sqlite` 保存绑定、轮询游标、消息、回复状态、原始转写和纠正稿。`state/weixin/attachments` 保存收发附件，绑定凭据由当前 Windows 账户加密。 |

保存其中一类不代表其他状态也回滚。Discard 不撤销已经持久化的消息、会话或已发生的外部副作用。

## 统一保存和退出

原生 `Smalltalk snapshot:andQuit:` 已接入本工程的监管流程。内部快照使用保留的原生实现，避免再次触发界面保存请求。

| 操作 | 当前行为 |
| --- | --- |
| Save | 等待新的检查点成功提交，再继续运行。 |
| Save and Quit 或退出框 Save | 收束当前模型调用，提交检查点，再结束整组本地进程。 |
| 退出框 Discard | 收束当前模型调用后退出，不额外提交本轮镜像。 |
| 退出框 Cancel | 不保存也不退出，留在当前环境。 |
| `stop.ps1` | 保存退出的命令入口。 |

需要在程序中主动保存执行现场时，在独立 Process 执行：

```smalltalk
[ LMExecution checkpoint ] fork
```

不要在通信邮箱的同步回调中等待检查点。调用模型之前客户端也会自动保存检查点。保存操作返回成功和文件存在、页面展示是不同事实，应以实际提交回执核对。

## 检查点如何恢复

`LMExecution checkpoint` 暂停发起它的业务 Process，由 GT 将运行现场保存到 `state/runtime/working/main.image` 与 `main.changes`。Windows 监管程序将其封存为新代次的 `resume.image`、`resume.changes`，刷盘并计算两者的 SHA-256，再原子更新 `state/runtime/current-image.json`。GT 收到成功回执后放行等待的程序。

首次没有检查点时使用初始 `state/runtime/main.image`；有检查点后以指针为准，启动先校验封存双文件。旧指针没有变更文件摘要时仍兼容读取，下次成功保存补齐双摘要。启动将封存镜像复制到 `state/runtime/working`，避免直接覆盖恢复依据。正常保存继续使用同一工作路径；若用户另存改变了活动镜像位置，下次检查点会切回工作路径。以 `Smalltalk imageFile fullName` 核对实际路径，不手工编辑恢复指针或原地改写封存的 `resume.image`。

重新启动时终止旧通信邮箱、重新绑定通信与线程，随后放行保存的业务进程。局部变量和执行位置可以从检查点继续，不必重跑整个方法。原生保存退出的等待调用者恢复时返回恢复状态，不会再次执行退出。只有成功提交的检查点是恢复依据；缺失或校验失败会阻止启动。

桌面启动时会清除镜像恢复出的旧退出提示。正常关闭窗口时仍会显示当次退出确认。

按用户要求，当前只保留**最近一份成功提交并校验通过的恢复代次**，以及运行需要的工作副本。工作副本会继续变化，不能与封存恢复文件使用硬链接。新代次提交前保留旧代次；提交、放行并验证成功后，自动删除其他受管 UUID 代次。保存失败不会清理上一份恢复依据。活动文件位于旧代次时受保护，清理不会沿目录链接进入外部资源，未知目录也不会自动删除。

每代只封存一对 image/changes，不再另存重复的 main 文件，也不逐代复制工具包源码参考与资源。正常保存退出复用当前恢复代次，不再在 `backups/snapshots` 累积第二份完整镜像。初始工具包与初始模板属于安装资源，独立保留。

`src/supervisor/Recovery.cs` 负责冷启动校验、封存和保留边界。最近一次自动清理见 `logs/checkpoint-retention.json`。清理失败记录并延后，保留已提交的保存结果。历史退出备份的一次性整理应先正常停止环境，再核对有效指针和运行文件。

## 会话与未决调用

SQLite 使用 WAL 和 `synchronous=FULL`。新线程在发送模型轮次前保存绑定。启动时，Loom 用已保存的绑定同步镜像中的线程 ID。打开已绑定的 Codex 会话时，续接失败会报告错误。对象调用的会话接手走本页的轮次恢复流程。

同一次模型调用的 request ID 在发送前随检查点保留。开始发送前登记调用，完成后保存结果：

- 已完成的调用恢复时复用原回执。
- 对象调用在确认结果工具之前另存一次检查点，保存原调用、实参及实际返回对象。轮次成功结束或在保存结果后明确失败时，已提交的调用回执会让等待中的 GT 程序从镜像取得同一个返回对象。后者的回执同时保留轮次失败状态及 `partialFailure`。
- 静默后提前交回对象时，回执带有 `ok: true`、`partialFailure: true` 和 `releasedAfterSilence: true`。此时轮次的最终状态尚未确认，回执没有 `turnStatus`。
- 已明确结束但缺少返回对象的正常或失败轮次，由共享调用层在同一 Codex 会话发起恢复。每轮独立登记，恢复请求用 `originalRequestId` 关联原调用。退出中断的轮次结束本次等待。
- 已开始但结果未确定的调用返回明确的中断或不确定错误，不能盲目重发。
- 尚未发出的请求可以继续处理。
- 显式新会话的决定与回执一起提交，旧回执重放不会再次切换。

未决的新线程创建也不能自动重复。恢复异常时查实际请求、持久绑定和回执；外部操作需要自身的幂等或结果核对，不因镜像恢复就假定只执行过一次。

## 同一生命周期

桌面快捷方式的 `open-loom.ps1` 仅等待启动脚本确认就绪并唤出窗口，随后立即结束。它不等待 Glamorous Toolkit 整个运行周期；启动后立即关闭窗口属于正常操作，不应报进程不存在。持续监管由独立的 supervisor 负责。

Windows 监管程序先把 GT 加入带 kill-on-close 的 Job，再放行执行。Codex App Server 和普通工具子进程继承同一组。GT 发现 Codex 连接故障时上报并退出。监管程序退出时 Windows 关闭 Job，结束其余本地受管进程。

Windows 监管程序监测 GT 心跳，通常在约 15 秒内发现 VM 卡死。检查点保存期间允许更长的停顿。正常停止按保存流程退出，异常退出从最后提交的状态恢复。新进程使用独立的启动标识，旧镜像中的通信或退出业务栈无法继续操作本次运行。

Windows Job 管理本机执行器和受管进程，远端请求仍按调用回执核对。不要另起脱离当前监管的 Codex 来继续当前工作。发现旧实例留下的进程记录时，当前启动脚本会核对程序路径和参数，再清理属于该实例的残留进程。

从 Loom 旧专用目录升级时，正常保存退出后由下一次启动执行单次迁移。启动脚本复制旧目录中已登记的线程记录并保留线程 ID，随后使用 Codex 的续接接口核对结果。Codex 在用户数据目录建立索引并保存线程名称。迁移成功回执在 `state/sessions/codex-home-migrated.json`，之后启动直接使用 Codex 的用户数据目录。已有用户配置、登录和其他线程继续由 Codex 管理。

## 模型轮次等待

连续 30 分钟未收到同一轮次的新进展时，Loom 追加一条活动记录。业务结果已持久化时，Loom 请求中断并立即交回已保存的对象，调用回执记为部分异常，原 Codex 会话绑定继续有效。旧轮次的结束事件用于释放后续模型请求，已交回的业务结果无需等待此事件。尚未保存结果的对象调用同时进入后台网络探测，流程见 [对话程序与调用机制](02-对话程序与调用机制.md#流式回复与活动历史)。退出时请求中断活动轮次，进程或连接故障仍按运行时故障路径处理。协议握手、工具回调及心跳检测各有自己的故障检查。共享调用层的恢复循环以收到明确的轮次结果为前提。

自动或手动请求新 Codex 会话接手时，注册表先记录旧请求及会话。只有旧轮次的结束回执已保存且仍缺返回对象，恢复请求才可以清除旧绑定，启动新会话创建。清除旧绑定和登记恢复请求在同一事务中提交。新会话创建继续沿用 `creating` 状态及绑定回执，断开后结果不确定时须先核对。Loom 尚未收到旧轮次的 `turn/completed` 时，后续轮次保持等待，已提前交回的业务结果仍以持久回执为准。

GT 客户端在一次运行中负责模型连接。热更新后，已经进入旧方法的调用仍可以继续执行旧逻辑。
